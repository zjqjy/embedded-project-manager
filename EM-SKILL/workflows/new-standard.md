# 工作流: new 中档（standard）— R0/R1/R2/R3 追问先行、落盘最后

> 适用：跨模块特性、需设计但非系统级（默认档位）
> 产出：`features/S<N>-<slug>/plan.md`（1 个文件，「方案」与「拆分」两章）
> S18 起升级为四轮：**R0 追问 → R1 方案 → R2 拆分全程对话，唯一落盘批次在 R3**——人工未确认理解之前不写任何文档。

## 核心理念（借鉴 superpower + spec-kit，S18 调研）

**clarify → brainstorm → plan → execute**，前三轮纯对话，写文档是最后一步：

```
R0 追问轮（一次一问，下限 ≥2、不设上限）→ 用户确认理解摘要
        ↓（全程不落盘）
R1 方案对比对话轮 → 用户选定方案
        ↓
R2 拆分对话轮 → 用户确认子步骤
        ↓
R3 统一落盘（唯一落盘批次，逐一确认）→ 提示 verify
```

## R0: 需求澄清（追问轮，新增）

**执行 `workflows/new-clarify.md`**（三档共用规范）：一次一问、选择题优先、**下限 ≥2 问、不设上限**（以 AI 判断意图清晰为退出条件）、高影响优先；
无论问多问少，以**需求理解摘要经用户确认**收尾。确认前禁止输出方案草稿、禁止创建任何文件。

R0 得到的 Q→A 全部带入 R1（作为方案设计的输入），最终并入 plan.md 方案章「需求理解」。

## R1: brainstorm（发散，纯对话）

**目标**: 用 ~3 个候选方案对比，选定方向。

**规则**：草稿**只在对话中呈现**，本阶段**不创建 feature 目录、不写任何文件**（落盘统一在 R3）。

**AI 对话输出格式**（非文件内容）：

```markdown
## S<N>-<slug> 方案对比

### 方案 A: <名字>
- 思路：<一段话>  优点：…  缺点/风险：…  工作量：<S/M/L>

### 方案 B: <名字>
（同上）

## 推荐: 方案 <X>，理由：<一句话>
```

提示：
```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
✅ 输入 `继续` 采用推荐方案 → 进入 R2 拆分
🅰️🅱️ 输入 `A` / `B` 选别的方案
✏️ 输入 `补充: <...>` 添加缺失方案/约束
🔄 输入 `回到 R0` 需求理解有误，重新澄清
❌ 输入 `取消` 退出
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## R2: milestones（收敛，纯对话）

**目标**: 把选定方案拆成可独立 verify 的子步骤。

**约束**:
- 子步骤数量 ≤ 5（否则建议升档 deep）
- 每个子步骤必须可独立 verify

**AI 对话输出**：子步骤清单（ID / 名称 / 依赖 / 验证方式 / 预估），

提示：
```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
✅ 输入 `继续` 采用拆分 → 进入 R3 统一落盘
🔧 输入 `合并 A B` / `拆分 A` 调整
✏️ 直接口述修改
❌ 输入 `取消` 退出
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## R3: 统一落盘（唯一落盘批次）

R0-R2 全部对话完成后，**先展示每处将写入的内容摘要，用户确认一批写入一批**：

| # | 落盘点 | 将写入的内容 | 确认方式 |
|---|--------|-------------|----------|
| 1 | `features/S<N>-<slug>/`（创建目录） | README 状态卡（templates/feature-README.md）+ `plan.md` **一次成文**：`# plan` + `## 方案`（需求理解含 R0 Q→A + 全部候选 + 选定理由 + 关键技术点）+ `## 拆分`（选定方案复述 + 子步骤表 + 关键决策）+ `status.json` | 展示 plan.md 目录级摘要 → `继续` |
| 2 | `state.md` | 当前步骤 = S<N>-A、下一步动作 = 编码后 `/em verify s<N>-a`、追加最近决策 | 展示 diff 摘要 → `继续` |
| 3 | 步骤索引 | **v4**：`features/README.md` 步骤总表追加一行；**v3**（未迁移）：`project-spec.md` 步骤表追加（文件不存在则先从模板创建，S17-A 首次写入原则） | 展示行内容 → `继续` |
| 4 | 决策记录 | **v4**：`journal.md` 追加选定方案关键决策 1-3 条；**v3**：`decisions.md`（不存在则先创建） | 展示条目 → `继续` |

> v3/v4 判定：`<STATE_DIR>/features/README.md` 存在即 v4。
> 用户说「都写」可一次确认四处；任何一处有异议就单处修改后重确认。

```
🎯 选定方案: <名字>
📦 子步骤数: <N>

━━━━━━━━━━━━━━━━━━━━━━━━━━━━

下一步:
  开始编码 S<N>-A → 完成后 /em verify s<N>-a
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 升降档触发

| 触发 | 建议 |
|------|------|
| R0 追问发现「这就是个 bugfix」| 降轻档（`--light`），R0 结论保留在对话即可 |
| R0/R1 发现「涉及新外设/协议栈」| 升重档（`--deep`），追加 hardware/requirements 讨论 |
| R2 子步骤 > 5 | 升重档，做子流程拆分 |

## 与 S16/S17/S18 的关系

- R1/R2/R3 渐进确认流 = S16-A「落盘前必须确认」设计（S17-A 收编落地）
- S18 在其前插入 R0 追问轮、并把 R1/R2 的落盘点后移合并进 R3（「最后一步才写文档」），产物形状不变
